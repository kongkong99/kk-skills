# Product benchmark to execution tasks

Help the user move from a benchmark product to an execution plan for their own product. Preserve the user's product idea, constraints, and stated scope; a benchmark informs choices rather than determining the result.

## Establish the target

Identify the intended user, problem, desired outcome, product form, and constraints that matter to the plan. Use context already provided. Ask only for missing information that would materially change the choice of benchmark or scope; otherwise state reasonable assumptions and proceed.

If the user supplies a benchmark, analyze it. If they ask to find one, search current public sources, compare plausible candidates on target user, core problem, product form, and observable information, and explain the selection. If evidence is insufficient, mark the choice provisional. Respect a user's specified benchmark or alternatives.

## Investigate the benchmark

Use accessible primary sources such as the live product, official documentation and public demonstrations; search the web when necessary. Trace the main user journey from entry through the desired result, and record relevant functions, interactions, business rules and dependencies. Adapt depth to the user's goal and accessible evidence, rather than exhaustively cataloging the entire product.

Separate observed facts with links from inferences, unknowns, and ideas for the user's product. Do not claim to have tested a workflow or seen internal implementation when access is unavailable. Identify important gaps and propose practical ways to validate them.

## Translate to the user's product

Map the benchmark's capabilities to the user's target: retain, adapt, defer, or exclude, with a brief reason. Identify a smallest coherent first release that delivers the core user outcome. Distinguish required work from optional enhancements, and indicate decisions that depend on research or user input. Do not assume that similar appearance implies the same internal design.

## Build the execution plan

Organize tasks by user journey and dependencies, grouping where useful into product, design, engineering, content, testing, or operations. Tailor categories to the project. For each task include:

- A concrete action and expected output.
- A checkable completion criterion; add a validation method when it is not obvious.
- Dependencies and priority or milestone where useful.
- Open decisions or assumptions that block execution, if any.

Split work until each task has a clear deliverable and can be assigned and verified; avoid artificial time estimates or inventing a tech stack. Make prerequisites and parallelizable work visible. Mark estimates as estimates when the user requests them and enough information exists.

Present the selected benchmark and evidence, the proposed first-release scope, and the ordered task list. End with the most useful next action and any decision that genuinely prevents further progress. When the user requests implementation, use the plan to proceed within the authorized scope rather than stopping after planning.
